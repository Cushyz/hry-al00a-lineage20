# init 中的机型名解析修复

## 根因与证据强度

正常启动的两份早期日志最后都到达 `libinit_variants: load_variants`。单靠这行日志只能定位阶段，不能证明具体越界。进一步只读解析本台 OEMINFO 和反汇编该 ROM 的 init/libc，得到以下一致关系：

- 记录 ID `0x61`、记录版本 6，机型内容 `HRY-AL00a`，长度 9 字节。
- ROM 分配 8 字节缓冲区，以实际长度 9 和容量 8 调用 `__memcpy_chk`。
- 对应 libc 在长度超过容量时进入失败并 abort 的路径。
- 后续还将结果构造成 8 字节短字符串，仅修改检查容量或仅修改分配都不完整。

局部离线测试通过；现场应用完整补丁后 Android 从循环重启变为进入桌面，之后移除诊断 kernel 仍可启动。这些是本次归因的依据，不声称从日志里直接捕获到了完整的 abort 堆栈。

## 精确版本约束

原始文件：从测试 ROM 的 system 镜像提取 `/system/bin/init`，2308120 字节。

```text
原始 SHA256
503623323e7359f6504dbe78610168076fd5d9d70e58958e054b5f1ddfb5f31a

修复后 SHA256
379a9bbf5a920aacfdc8805caafd34334fc6c3f8e2f89229fa0b15c01e1dcbe1
```

仅接受完全相同的原始文件，不能把偏移应用于其他 ROM 构建。

| init 文件偏移（十六进制） | 原字节（小端） | 新字节（小端） | 作用 |

| 0x152798 | 00018052 | 00028052 | 分配 16 字节 |
| 0x1527b0 | 1f0000f9 | 1f7c00a9 | 清零整个 16 字节缓冲区 |
| 0x152b84 | 03018052 | 03028052 | checked-copy 真实容量设为 16 |
| 0x152db0 | 09028052 | 09048052 | 此二进制的短字符串长度编码改为 16 |
| 0x152dbc | 6a0240f9 | 6102c03d | 读取完整 16 字节 |
| 0x152dd4 | ca1200f8 | c112803c | 写入短字符串数据 |

已有 find(NUL)/substring 逻辑去掉零填充，保留完整 `HRY-AL00a`。容量检查继续存在；不是关闭 FORTIFY 或跳过机型初始化。Q1 的使用经过现场代码范围分析，不跨越需要保留的活跃寄存器值；不能脱离此版本套用。

汇编见 [changes.S](../patches/changes.S)，机器可读描述见 [补丁清单](../evidence/init-patch.json)。离线生成器见 [patch-init.py](../scripts/patch-init.py)，只输出普通文件，不访问手机。

## 如何验证

历史验证包括：

1. QEMU AArch64 局部测试长度 0、8、9、16，长度 17 按 checked-copy 比较分支拒绝。这是隔离测试，不是完整 Android 启动模拟。
2. 在 ext4 副本已有数据块内修改，`e2fsck -fn` 通过；重新导出的 init 与目标一致。
3. inode 元数据、权限、属主、extent 和可见 SELinux xattr 保留。
4. 设备写入前完整核验原始 init，写后完整回读得到上述修复后 SHA256。
5. 用户确认进入设置向导及桌面；移除诊断 kernel 后仍正常。

`patches/test.S` 保留局部汇编测试。新发布的普通文件生成器额外拒绝未知哈希、设备节点、同路径和覆盖现有输出。

## 为什么没有发布“一条 dd 命令”

原始现场的 system 文件系统块 73749，恰好映射到物理 system 载体的 74005 块；块大小 4096。这个对应关系来自**当时设备的实际 LP 元数据**，不是机型规格保证。

不同安装顺序、liblp 分配结果、ROM 或 ext4 变化都可能改变映射。文件偏移、ext4 逻辑块与物理载体块是三种不同坐标。不能把上面的表当作磁盘写入偏移。

复现手机写入需要重新读取并验证：真实载体身份和大小、LP 主/备份元数据、logical extents、文件 inode/extents、挂载状态、完整原始文件哈希；备份并确认写后完整哈希。原私有脚本还绑定设备序列号及元数据前缀。去掉这些检查直接公开会失去其适用前提，所以当前仓库只发布离线算法。

将补丁集成进 ROM OTA 可以作为后续工作，但本次没有验证这个新安装路径。不要把离线生成 `init.patched` 视为已修改 ZIP 或已修改手机。

恢复原始 init 会重新引入问题。日常更新、重刷原包或容量适配旧包也可能覆盖修复。成功后应保留可回退材料，而不是立即还原 init。
